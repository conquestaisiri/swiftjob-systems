# Root causes and repair dependencies

1. **Ownership is confused with knowledge of an application reference.** The public application endpoint returns an ID for any supplied email; password registration then treats that ID/email as ownership. Require an authenticated verified-email session, derive the email from that session, and expose password setting inside the portal. Repair login's double-signed session and logout revocation in the same batch.
2. **Shared JSON parsing calls itself.** Valid JSON mutations fail across contact, assessments and administration. Repair the shared boundary and test valid, malformed, null and array payloads across representative routes before broader workflow tests.
3. **State and validation rules are divided between UI and services.** Job eligibility, CV rules, duplicate submission, assessment completion and private room publication are inconsistently enforced. Move authoritative checks to the server and keep frontend guidance consistent. Preserve SQL ownership and one-use token safeguards that already work.
4. **Async work lacks durable state and a consistent success contract.** Void email returns are mistaken for failures; retries lack idempotency; some background writes are not attached to Worker lifetime. Define accepted/failed outcomes and event identity, then verify operator-visible failures and safe retries.
5. **Claims and verification screens exceed implemented behavior.** Fabricated client placeholders, unsupported country counts, contradictory optional checks and simulated technical verification undermine trust. Remove unsupported representations, retain useful features with honest labels and explicit user actions, and align legal/product copy with actual data handling.
6. **Shared contracts and release checks are incomplete.** Retired code, duplicate schemas, dynamic DDL, inconsistent configuration, missing semantic tests and broken package-manager setup allow type-correct regressions to ship. Add meaningful connected tests and explicit migration/release checks before deployment.

Repair order: A authentication/JSON boundary; B application/storage/state integrity; C assessments/next steps/privacy; D email/event reliability; E public navigation/copy/accessibility; F admin and responsive regressions; G release/SEO/performance/configuration. Findings and exact batch scope must be recorded before edits. Later discoveries may refine dependencies without silently expanding a batch.
